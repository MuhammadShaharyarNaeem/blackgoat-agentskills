# Privacy Engineering Patterns

A privacy policy is a promise; the code is whether it was kept. This contract turns each promise into a control with an artifact behind it: data you have located rather than assumed, a consent flag the write path actually reads, a deletion that reached every store and was re-queried afterwards, and a retention clock something runs. Every claim here is closed by an evidence artifact, never by a reviewer's confidence.

## Worker Execution Contract

This is the operational spine. Follow it as written.

### Scope, and the sibling this refines

`{PLUGIN_ROOT}/security-and-hardening/references/data-privacy-checklist.md` owns the **audit** side of personal data: PII classes, forbidden placements (logs, URLs, analytics), a stated retention rule per store, a deletion path that is exercised at all, log-redaction captures, and the third-party flow inventory. Read it; never restate it here.

This skill owns the **engineering** side — the controls that make those audit lines passable — and two of its rules are deliberately tighter than that checklist's (convention #8, naming the rule refined):

- *Deletion path exists and is tested* proves **one** path runs. § Deletion Propagation requires the fan-out to reach **every** store in the inventory and be confirmed by a re-query afterwards.
- *Retention rule stated per store* proves a rule was **written**. § Retention Automation requires a **job that ran** on a named schedule.

The check names below are distinct from that checklist's, so both sets can stand in one report without the report gate's name-deduplication silently dropping one.

### 1. The Data Inventory

Nothing below is executable without knowing where personal data lives, so the inventory is built first and every other control cites it. It is a table, one row per field, saved at `.docs/{project-name}/implementation/privacy/data-inventory.md`:

| Field | Class | Store(s) | Lawful basis | Retention | Delete path |
|---|---|---|---|---|---|

- **Class** — identifier, quasi-identifier, contact, financial, health, credential. A field may carry more than one class; list each. Quasi-identifiers are classified, not waved through: a zip/birthdate/gender trio re-identifies most people, so "we removed the name" is never the label *anonymized*.
- **Store(s)** — enumerated from the scan, not from the schema alone. The stores that get missed are the ones nobody models: read replicas, warehouses and lakes, search indexes, caches, message queues, object storage, application and access logs, error and trace payloads, analytics event streams, backups, and third-party systems.
- **Lawful basis** — the named basis and purpose. "Might be useful" is not a basis; a field with no basis is a finding, and the remedy is to stop collecting it, not to document it better.
- A field the scan surfaced but nobody can classify is `UNCLASSIFIED` in the table and an `Important` finding — never omitted. Unclassified PII is unmanaged PII (`base-persona.md`, Evidence Integrity: an unscanned store is `BLOCKED`, not an empty row).

The inventory is **generated by a scan and then edited**, never typed from memory, and the scan is re-run each audit round — free-text columns, cache keys and log fields drift into holding PII nobody declared.

### 2. Consent at the Write Path

Consent is recorded in one place and enforced in another; only the second one is a control.

- **The enforcement point is the write or use site**, not the preference screen and not the reader. A stored opt-out that no writer checks is theatre.
- **A write with no recorded basis is rejected, not logged.** Proceeding-and-warning is the failure mode this rule exists for: the record lands, the warning scrolls past, and the violation is now in the store. Rejection is the default; an allowed-with-exception path is a named, documented exception, not a log level.
- **Consent is purpose-scoped and versioned.** `analytics`, `marketing` and `personalization` are separate grants, each carrying a timestamp and the policy version it was given under. A single boolean cannot express purpose limitation.
- **Pseudonymize before the data crosses the trust boundary.** A pseudonymized identifier is still personal data while the mapping exists — it lowers the blast radius, it does not remove the field from the inventory.

### 3. Deletion Propagation

An erasure request is complete when every store in the inventory no longer returns the subject, and that has been observed.

1. **Resolve locations from the inventory**, never from recall. A store absent from the inventory is a store the deletion will miss.
2. **Dispatch an idempotent, retried delete to each** — primary, replicas, warehouse, search index, cache, queues, third parties via their deletion API, and backups per the policy (tombstone plus delete-on-restore where a backup cannot be rewritten).
3. **Collect each store's ACK** and track partial progress. An ACK is a claim by the receiver.
4. **Re-query the identifiers across every store, and cite that output.** This is the evidence. An ACK set is not: it says each system believed it deleted, which is exactly what a silently-failing delete also says.
5. **Write the audit record** — what was deleted, from where, when, and the request-to-done duration against the SLA.
6. **Exclusions are explicit.** Data retained under another legal obligation (financial records, fraud holds) is listed with its basis in the audit record. A silently skipped store is indistinguishable from a missed one.

### 4. Retention Automation

Each store holding a PII class names the **schedule** that expires it — the job, its cadence, and its last successful run. A retention period enforced by someone remembering to clean up is not enforced. Absence of a schedule for a store holding a financial, health or credential class is `Critical`; otherwise `Important`.

### 5. The Data-Flow Map

One diagram or table of every flow personal data takes across a boundary — to a third party, to another region, or to a new purpose — each with its lawful basis and processing agreement. The evidence cites this map by path; a flow observed in the codebase and absent from the map is a finding, because a silent new data flow is how a violation starts.

Save it at `.docs/{project-name}/implementation/privacy/data-flow-map.md`. Design review is where it is cheapest to change: a feature that copies profiles into three services creates three deletion obligations, and scoping it to a reference creates none.

### Check lines in the privacy report

The report is `.docs/{project-name}/implementation/privacy-report.md`, one `## Privacy & Compliance Audit: <scope> — <date>` section per round.

**The line grammar — field order, status tokens, the evidence each status must carry, and the closing `**Verdict:**` arithmetic — is owned by `{PLUGIN_ROOT}/pipeline-tools/SKILL.md` § `check_agent_report.py`.** Read it there; never restate it and never invent a variant. Captures live under `evidence/privacy/`. This skill names only the checks and what each must prove:

| Check name | Its capture must be a recording of |
|---|---|
| `pii-inventory` | the discovery scan across the store list in § 1 — its counts are the inventory's row count and the `UNCLASSIFIED` count |
| `consent-write-path` | a test that attempts a write for a purpose with **no** recorded basis and observes it **rejected** |
| `deletion-propagation` | the **re-query** across every store after an erasure run — residual identifier count, which passes only at zero |
| `retention-schedule` | the expiry job's run or scheduler listing, showing the last successful run per store |
| `data-flow-map` | the outbound-integration enumeration compared against the map's declared flows |

Each executed line is captured with `run_quiet.py --capture .docs/{project-name}/implementation/evidence/privacy/<check>.md --ledger .docs/{project-name}/implementation/gates.jsonl -- <the command>`. A check whose precondition is absent is `BLOCKED` with its reason — never `PASS`, never omitted.

### Which rules are gates, and which stay prose

Convention #9: a rule that asks for restraint at the moment of approving is enforced by an artifact, not by wording.

**Converted.** The two approvals this skill exists to prevent are *declaring a deletion complete* and *declaring consent enforced*. Both convert through the report gate rather than a new script: `check_agent_report.py` ties a check line to the capture of **the command the line names** (`capture_command_mismatch`, for which there is deliberately no waiver). So `deletion-propagation` naming the re-query as its command means an ACK log cannot be cited in its place, and `consent-write-path` naming the rejection test means a code read cannot. The restraint is now a file that has to exist and hash correctly, not a sentence.

**Staying prose, with the reason.** Field classification (§ 1), minimization at collection, and the choice of pseudonymization versus aggregation versus differential privacy are design judgements made once, at a moment with nothing to approve — there is no "mark it complete" instant for a gate to sit at, and a script that counted classified fields would grade the inventory's length, not its correctness.

### Escalate When

- A store in the inventory has no delete path, or a third party has no deletion API → escalate to the Orchestrator; do not verdict the erasure complete.
- A field's lawful basis cannot be established → escalate rather than assign one.
- A dataset is about to be labelled *anonymized* without a re-identification test → escalate; the label is a claim, not a transformation.
- A new flow sends a PII class across a boundary with no processing agreement → escalate before it ships.
