# The Audit Heuristics (Deep Dive)

When auditing an agent's persona and methodology files, apply the following metrics systematically. These heuristics are designed to detect logical deadlocks that cause LLM-based agents to hallucinate, crash, or disobey instructions.

**Metric families (stated once here, not restated per metric).** Some metrics share one principle and differ only in where they look. Each section below carries only its own distinct check.

- **Context economy — 3, 8, 10.** Unconditionally-loaded generic text crowds out the project-specific reasoning the agent was spawned to do. 3 looks at what the persona *knows*, 8 at what it *loads*, 10 at the *measured number*.
- **One rule, one home — 5, 6, 18.** A rule stated in two places will be edited in one. 5 catches a formatting rule contradicted by its methodology, 6 catches a whole contract copied per role, 18 catches one *idea* restated in N places where no two sentences match.
- **Existence vs. agreement — 15(c), 16, 17.** 15(c) is the general heuristic (is this contract documented at both ends?); 16 and 17 are hand-kept inventories of specific named instances. An inventory catches only what someone listed; the general heuristic catches the next unlisted case. 16 and 17 are existence checks on the *mechanisms* — they never score a pipeline's output documents.
- **Numbers are permanent.** Metric numbers are cited across the plugin (`CLAUDE.md`, recorded decisions, sibling skills). Never renumber to tidy up; append only.

## 1. Interface Alignment (Input/Output Collisions)
**Definition**: The output expected by a downstream agent must perfectly match the actual output format produced by the upstream agent.
- **Why it matters**: Agents do not have common sense. If Agent B's skill tells them to extract the "Definition of Done" from a plan, but Agent A (the planner) was updated to output "Acceptance Criteria" instead, Agent B will either fail, hallucinate a Definition of Done, or loop infinitely.
- **Example**: Mason's persona instructed him to read the "Definition of Done" from Alex's plan, but Alex had been updated to drop the DoD format.
- **Writer ownership (the collision on the output side)**: every pipeline artifact must have exactly one declared writer. Two skills naming two different actors as writers of one path is an output collision — the earlier writer's content is destroyed with no error, no conflict marker, and nothing in either file admitting the other exists. "Append" does not save it: the defect is that two files give two different answers to "who owns this path", so the next edit to either side can reintroduce an overwrite. Phase-order matters as much as writer count — an artifact written in an earlier phase than the phase whose owner creates it collides even with a single named owner.
- **Example**: a newly added Brief-Conformance Diff let the Architect append its table to *either* `detailed-design.md` or `design/design-review.md`, while the pipeline separately declared `design-review.md` the Orchestrator's later-phase output and told it to "write" (not append) that file. Two good rules, installed days apart, collided on installation; the Architect runs first, so the Orchestrator's write would have silently erased her table.

## 2. Dependency Conflict Detection
**Definition**: A global/inherited methodology (like `base-persona.md`) must not mandate rules that contradict the agent's core identity or capabilities.
- **Why it matters**: Over-broad global rules often break specialized agents. If a global rule forces an XML `<handoff>` structure, but a builder agent's local persona forces a `<changed_files>` XML structure, the agent will suffer from cognitive dissonance and likely output corrupted XML.
- **Example**: `base-persona.md` instructed *all* agents to save their final output to the `.docs/` folder. This broke Mason, who is an execution agent whose entire job is to write code in `src/`. The fix was forking the dependency into a Planner persona and a Builder persona.

## 3. Role Cohesion (The Bloat Test)
**Definition:** Agents must only know what they need to know to do their job. Global personas should not be bloated with framework-specific syntax or project-specific procedural memories unless they are specialized agents for that exact framework.

**The Abstraction Rule:**
Auditors must NOT blindly delete all Procedural Memories. Instead, use the Abstraction Rule:
- **Elevate**: Universal Engineering Principles (e.g., Separation of Concerns, Data Safety) must be KEPT and ideally elevated into the agent's core Responsibilities.
- **Abstract**: If a rule is highly specific (e.g., Docker specific), attempt to *generalize it* into a language-agnostic software engineering principle (e.g., "Verify environment configurations drop privileges safely") before deciding to move it.
- **Purge/Move**: Irreducible, hyper-specific project bloat that cannot be generalized must be moved to the project's `.agents/AGENTS.md`.

**Red Flag:** The global persona contains specific instructions for React, Docker, or Terraform, even though the agent is meant to be a generalist code reviewer or planner.

**Real-World Example:**
*Luna (Reviewer)* had a procedural memory dictating how to parse Vue.js global state mutations and specific Docker health checks. The auditor applied the Abstraction Rule, abstracting the Docker check into a general "Infrastructure & CI/CD Security" responsibility, and moving the Vue.js specific rule to the project's `.agents/AGENTS.md`.

## 4. Escalation Hallucination & Path Validity
**Definition**: An agent must have a physically possible chain of command to escalate blockers. Furthermore, isolated subagents must not be given instructions to manage workflow state transitions (e.g., "proceed to Phase 2").
- **Why it matters**: Subagents running in isolated workspaces cannot magically invoke other subagents or transition pipeline states. They can only communicate back to their caller.
- **Example 1**: Mason's skill instructed him to "escalate to Aria" if he encountered an architectural blocker. Mason lacked the tools to spawn or message Aria. He must be instructed to escalate back to the Orchestrator.
- **Example 2**: A research methodology tells an isolated subagent to "ask the user for approval before proceeding to planning." The subagent doesn't control the pipeline; the Orchestrator does. This causes severe Role Dissonance.

## 5. Token Efficiency (Formatting Micromanagement)
**Definition**: Agents should not be burdened with overly strict, redundant, or conflicting formatting templates.
- **Why it matters**: Fighting formatting constraints wastes token context and degrades reasoning performance. If a methodology dictates a tagging format, the persona should not try to invent its own hierarchy.
- **Example**: Alex's persona forced him to use `[LOW]/[MED]` tags and a `1.1` hierarchy, while his methodology forced `[SEC]/[EXT]` tags and a `Task N` hierarchy. By stripping the formatting rules out of the persona and deferring entirely to the methodology, Alex's reasoning capabilities improved dramatically.

## 6. DRY (Don't Repeat Yourself) & Contract Reuse
**Definition**: Methodologies (like a code simplification matrix) should be role-agnostic and shared. Do not duplicate a contract just to change the instruction verb (e.g. from "rewrite" to "flag").
- **Why it matters**: Duplicating a methodology creates a maintenance nightmare. If you add a new pattern later, you have to update multiple files. This is how codebases rot.
- **Example**: Instead of creating a `code-simplification-reviewer-contract.md` for Luna and a `code-simplification-builder-contract.md` for Max, keep one role-agnostic methodology. The *Persona* dictates the interaction rule (Luna's persona is told to "audit only", Max's persona is told to "execute the rewrites").

## 7. Orchestrator vs Methodology Collision (Workflow Dissonance)
**Definition**: A Methodology (`HOW` a task is done) must not attempt to orchestrate the swarm, manage multi-agent state transitions, or spawn subagents. That is the exclusive job of the Orchestrator.
- **Why it matters**: If a methodology is written as if the subagent is managing the entire workflow (e.g., "Step 1: Plan, Step 2: Spawn workers, Step 3: Synthesize"), but the Orchestrator is *also* trying to manage those steps from the outside, the subagent will get confused and skip steps.
- **Example**: The `blackgoat-research` methodology told Aria to conduct the research herself, while the `bgpdd-plan` Orchestrator was trying to spawn Scout workers to do it for her. The fix is to split the methodology into discrete "Modes" that the Orchestrator can explicitly trigger (e.g., Mode 1: Plan, Mode 2: Synthesize).

## 8. Context Bloat & File Bloat (The Wake-Up Tax)
**Definition**: A persona must strictly limit how many Methodology Dependencies (each a skill's `SKILL.md`) it forces the agent to read at startup. 
- **Why it matters**: reading methodologies at runtime guarantees the agent gets the exact text (avoiding Orchestrator hallucination) — that guarantee is what this metric prices. Loading five heavy files "Always" pays it on every wake, for text most wakes never need.
- **Example**: A persona should not load `godot-gdscript-patterns/SKILL.md` "Always". It should explicitly state: "When evaluating external libraries or APIs" or "If the project uses Godot Engine". Only the absolute core rules should be loaded unconditionally.

## 9. ID Traceability (The Golden Thread)
**Definition**: Requirements must generate stable, verifiable IDs (`FR-1`, `NFR-1`, …), and those IDs must be explicitly threaded through the entire pipeline — the requirements stage assigns them, planning tasks cite them (`Requirements covered: FR-…`), tests exercise them, and coverage gates check them.
- **Why it matters**: Prose-matching ("the test checks the login feature") is unverifiable. ID traceability enables hard boolean gates: a planning-coverage gate (every Must-Have `FR` maps to a task) and a build-coverage gate (every Must-Have `FR` maps to a passing test). If any link in the chain drops the ID, those gates silently pass on incomplete work.
- **Example** (blackgoat squad): Rex's `requirements.md` assigns the IDs, Alex's `plan.md` tasks cite them, Quinn's tests exercise them, and the bgpdd-plan Phase 3.5 + bgpdd-build Build Coverage gates check them.

## 10. Wake-Up Context Weight (Quantified)
**Definition**: Measure, don't guess. For each audited agent, count the words of its persona file PLUS every "Always"-loaded Methodology Dependency (e.g. via `wc -w`). Flag any agent whose unconditional wake-up load exceeds ~2,500 words, and any methodology `SKILL.md` that is not a lean spine (`## Worker Execution Contract` + `references/` deep-dive per the house convention).
- **Why it matters**: this quantifies Metric 8's qualitative check. A persona can *look* lean while its "Always" dependencies quietly stack thousands of words into every wake-up. A hard number makes the bloat undeniable and the fix measurable.
- **Example**: Luna's wake-up load was ~3,600 words (persona + base-persona + a 2,360-word code-review methodology full of human-team process advice like "respond within one business day"). Spine-splitting the methodology cut her load by a third without losing any contract rule.
- **Recorded decision (2026-08-01)**: Alex's and Aria's wake-up loads are accepted deviations above this metric's ~2,500 guideline — measure them at audit time rather than trusting any number written here; both sit meaningfully over. Both have been through spine-splits and persona dedup/slimming passes (2026-08-01) that removed all relocatable rationale and pure restatements; what remains is normative contract needed on every wake — Alex: the task template and verification checklist; Aria: the design template's obligations and her architecture-judgment bar — plus base-persona (~1,000 words, shared by every agent). The ceiling is arithmetically unreachable for either without moving always-needed contract to on-demand loading, which would hide the cost rather than remove it. This is deliberately looser than the metric's guideline for these two agents only. Report each as a Warning; re-open only if base-persona shrinks, their contracts shrink, or non-contract prose re-accumulates in their spines.

## 11. Frontmatter & Metadata Hygiene
**Definition**: Frontmatter must be internally consistent across the squad: `phase:` labels form one coherent, collision-free sequence; `model:` tiers exist and fit; `description:` matches what the file actually does; `depends-on` names real agents.
- **Why it matters**: Stale or colliding metadata misleads both humans and the Orchestrator. If two agents claim the same phase, or a phase label contradicts where the pipeline actually runs the agent, delegation decisions are made on fiction.
- **Example**: `max.md` declared `phase: 3 — Refactoring`, colliding with Alex's `phase: 3 — Planning`, while the build pipeline actually ran Max in its Phase 4 — three contradictory answers to "when does Max run".

## 12. Trigger Collision
**Definition**: Skill `description:` fields are the triggering surface. Worker methodologies must not carry end-user trigger language that competes with the orchestrator pipelines. Worker methodologies must self-identify as squad-internal execution contracts; user-facing triggers belong to the pipeline skills.
- **Why it matters**: When a worker methodology's description advertises a user-facing trigger, it can hijack the trigger from the pipeline skill and run without any orchestration, gates, or squad — the user gets a bare checklist instead of the hardened SOP.
- **Example**: `shipping-and-launch` (a worker checklist) said "Use when preparing to deploy to production", competing with the `bgpdd-shipping` pipeline for the user's "ship it" — the methodology could hijack the trigger and run without any orchestration, gates, or squad.

## 13. Cross-Pipeline Consistency
**Definition**: Sibling orchestrator SOPs (e.g. the bgpdd-* pipelines) must share the same hardening skeleton: Path Resolution, Global System Constraints (strict delegation, phase-transition confirmation, artifact-verification chain-of-thought), Global Error Recovery + circuit breaker, state hydration/persistence (`orchestrator-state.json`), and a Game Tape evidence checkpoint (per-phase pipelines) feeding the single end-of-epic agent-improvement run (bgpdd-shipping). `orchestrator-state.json` is an inter-pipeline interface, not per-pipeline scratch: every field a downstream pipeline step reads must exist in the schema the upstream pipeline writes. Verify producer/consumer field-level completeness across sibling pipelines — a field written by one pipeline and silently absent when a sibling reads it is a Blocker (e.g. a git branch set in build but never persisted for shipping to consume).
- **Why it matters**: A pipeline missing pieces its siblings have is a latent Blocker: agents behave differently depending on which pipeline delegated them. The hardening skeleton is only a guarantee if every pipeline carries it.
- **Example**: `bgpdd-shipping` referenced `{project-name}` and deleted `orchestrator-state.json` yet had no hydration step establishing either, and lacked the error-recovery/circuit-breaker/improvement machinery all three sibling pipelines carried.

## 14. Model Assignment Fit
**Definition**: Each agent's `model:` tier must match its task complexity — lightweight scanners on small/fast tiers, architecture/planning/code-writing/meta-editing agents on top tiers, everything else mid-tier.
- **Why it matters**: A too-small model silently degrades output; a too-large one wastes budget on mechanical work. Neither failure announces itself — the scanner just gets slower and pricier, or the builder just gets subtly worse.
- **Example**: A haiku-tier model fits Iris's lightweight tech-stack scan; opus-tier fits Aria/Alex/Mason/Forge (architecture, planning, code execution, meta-editing). Assigning the scanner an opus tier or the builder a haiku tier would fail this metric.

## 15. Skill Content Validity & Cross-Skill Contract Coherence
**Definition**: A skill's documented content must be correct, not merely well-structured. Four checks: (a) Executable samples — every code sample compiles/runs against the real implementation it documents; a sample using an undeclared dependency or omitting required wiring/registration is a FAIL (e.g. a controller using an undeclared `_mediator`; `UseExceptionHandler` without the `AddProblemDetails` it requires). (b) Internal non-contradiction — the skill gives no two conflicting answers to one question, and no sample contradicts the skill's own doctrine (e.g. a ValidationFilter that bypasses the mandated response envelope). (c) Cross-skill contract coherence — this covers **any** producer/consumer contract spanning two skills, whether a runtime wire shape (a backend response envelope and its frontend consumer) or a document convention a tool parses (field grammars, ID formats, heading shapes). Check it in two steps, in this order. **Existence first**: the contract must be documented at BOTH ends. **Then agreement**: both ends must describe the SAME serialized wire shape and name the serialization policy that produces it (field names, casing, scalar-vs-object), NOT each side's source-language declaration shape; structured value types that must serialize as scalars require an explicit converter — verify the wire representation, never assume it mirrors the source. (d) Trigger cadence — a continuous obligation must not be phrased as a completion-conditioned one; a trigger clause ("when finished", "at the end", "once complete") gating an action that should be happening throughout teaches deferral.
- **Why it matters**: the other metrics check structure; none check whether documented content works or agrees with its sibling — a skill can pass every structural metric while shipping code that throws at startup or a consumer that silently misreads the contract (camelCase-vs-PascalCase makes `isSuccess` undefined → every failure treated as success). The existence half matters even more than the agreement half, and is newer: a machine-enforced grammar documented only on the **validator's** side is unreachable. An actor following its own methodology to the letter emits a shape the validator cannot match, so the check never fires — and a check that never fires is indistinguishable from a check that passes. That is why a one-ended machine contract is a Blocker, not a Warning. Check (d) is the same failure in the time dimension: a rule can be structurally correct and still teach the wrong *moment*.
- **Example**: a `consumes:`/`provides:` lint for plan task dependencies was installed with tests and fixtures on the parser side, but the producing planning methodology was left describing boundary contracts in free prose with no keyword grammar. The lint was real, tested, and permanently silent — a compliant planner could never emit input it could match. Metric 16 caught this one only because someone had listed it; per the *existence vs. agreement* family note, this metric is what catches the next one.
- **Example (d)**: `base-persona.md`'s "When your task is complete: save your final output" was structurally correct and destroyed two complete multi-call agent runs — it taught *when* to write, not merely *what* to write.

## 16. Defect-Class Enforcement
**Definition**: The pipeline's methodology skills must *contain* the defect-class enforcement rules that past escapes forced into existence. The inventory (verified against the live files 2026-08-01; grep the files, never this list):

- `blackgoat-research` — the `## Divergence & Supersession Register` design heading; the requirements write-back, now the *"a decision that makes any FR/NFR sentence false is a supersession"* corollary of the Self-Consistency Pass, carrying the phrase **NOT complete until** (both a register row AND an in-place `requirements.md` annotation); and the closing **Brief-Conformance Diff** step.
- `bgpdd-plan` — the Phase 2.5 Adversarial Design Gate with its 6-item attack list (crash windows, reversals, races, trust-boundary amounts, state-machine self-consistency, config knobs).
- `planning-and-task-breakdown` — the **observable-effects** rule and external-prerequisite ownership, now corollaries 1 and 3 of *"Plans model effects, not artifacts"* (human rulings included); the `provides:`/`consumes:` grammar the lint parses; the **negative-half proof** obligation on every gate-authoring task; the **declared-gate-needs-executor-wiring** rule (manifest script name AND CI job as task steps); and *"sequentially with a single builder"* (no task shaped around hoped-for parallelism).
- `pipeline-tools` — **four** lints with tests: `literal-count`, `consumes-provides`, `path-hygiene` (plan mode) and `supersession-annotation` (design mode).

A missing or weakened rule = FAIL naming the skill and the rule. **Scope limit on the fourth lint**: `supersession-annotation` checks register-rows → annotations, one direction only. It cannot see a divergence never filed, nor one filed outside the register section (an observed v8 run resolved a deleted-Cognito-attribute divergence in a §19 revision section and never annotated FR-29 — this lint misses that). Unfiled divergences remain the Phase 2.5 gate's job; do not credit this lint with that coverage.
- **Why it matters**: a rule installed in response to a real escape is the only thing standing between the pipeline and that defect class recurring, and its removal is completely silent — no run ever reports "the gate you added last month is gone". Every other metric asks whether the methodology is coherent; this one asks whether it still says the thing it was patched to say. Deleting the rule during an unrelated refactor costs nothing at edit time and everything on the next run.
- **Example**: adversarial review of two full `bgpdd-plan` runs (Travel-Goat v6 and v7) found **4 money defects** — a charge with no refund path, a hold-quota race, a crash window stranding paid bookings, and an unvalidated webhook amount — crossing design → plan with 100% fidelity and zero detection: every downstream stage faithfully transcribed a broken design. The same runs left `requirements.md` stale after the design overrode it, so the coverage gate certified a contract the design had already abandoned. The rules listed above are the direct response; this metric verifies they are still on disk. The next run of that pipeline (v8) then earned two more entries onto the list by demonstrating them load-bearing on live input: negative-half proofs were applied systematically to every gate-authoring task, and the declared-gate-needs-executor-wiring rule closed the "wired work nothing triggers" class twice in a single plan. Add an entry only when a rule has actually proven load-bearing on live input — the list costs maintenance, and per the *existence vs. agreement* family note the unlisted cases belong to Metric 15(c).

## 17. Output-Rubric Gate Coverage
**Definition**: Each of the 8 output-quality dimensions — brief coverage; structure & testability; honing quality; domain/financial correctness; completeness & reachability; infra answer quality; internal consistency & traceability; signal-to-noise — must map to at least one *enforcing mechanism* (a phase gate, a checklist item, or a lint) somewhere in the pipeline's methodologies. The question is "does a mechanism for this dimension exist", never "how good was this run". An uncovered dimension = **Warning**, not Blocker, naming the dimension.
- **Why it matters**: the rubric a reviewer uses to grade pipeline output is a map of everything the pipeline can get wrong. A dimension with no mechanism behind it is graded only when a human happens to read the output carefully — which is exactly how the v6/v7 defects survived. Warning rather than Blocker because not every dimension deserves a hard gate (signal-to-noise is judgment, not a boolean), so the metric surfaces the hole and leaves the maintainer to decide, instead of blocking on a gate nobody wants to build.
- **Example**: *domain/financial correctness* had no mechanism at all before Phase 2.5 existed — hence the 4 money defects. *Internal consistency & traceability* was covered only for `FR`/`NFR` IDs by the coverage gate, so hand-transcribed literal counts (a plan claiming 60 error codes against a design's 62) went unchecked and hard-stopped workers mid-task; the `pipeline-tools` literal-count lint now covers that half of the dimension.
- **Recorded decision (2026-08-01)**: for the `bgpdd-plan` pipeline, *signal-to-noise* is an accepted judgment-only dimension. Report it as a Warning and do NOT propose a gate for it unless a run shows concrete harm. This is a settled maintainer decision, recorded here so each audit stops re-litigating it — the Warning is expected output, not an open action.

## 18. Convergent Redundancy (Distillation)
**Definition**: When multiple rules, bullets, or lines across a persona or methodology encode the same underlying thinking, flag the cluster as a distillation candidate. The fix has three moves, and a real distillation makes all three: **merge the prose upward** into one stated principle with corollaries; **push the enforcement downward** into a mechanism (a lint, a gate attack item, a schema or template constraint); **move rationale to `references/`**. Severity: **Warning**; cite the cluster's lines and name the shared principle.
- **Why it matters**: accreted same-thinking prose is how contracts exceed their context budgets while getting weaker — each restatement is one more place the next edit forgets. It never looks like duplication, because no two sentences match; only the thinking behind them does. That is what separates this from Metric 6 (one contract copied verbatim into two files, which greps will find) and from Metric 5 (two formatting rules that visibly contradict). It is also the only metric whose *fix* is constrained: a distillation that merges prose without landing a mechanism has traded enforcement for brevity, and a renumbering "cleanup" breaks every citation elsewhere in the plugin — merge the text, keep the numbers.
- **Example** (the 2026-08-01 pass, three real clusters):
  - `blackgoat-research` step 6 carried five sub-rules that were each an instance of one idea — the document must be true wherever a reader lands. Merged into that principle with the five as named corollaries; rationale to `references/research-deep-dive.md`; enforcement landed as the `supersession-annotation` lint in `pipeline-tools --design`.
  - `agent-squad/orchestrator-contract.md` had *green is not evidence* and *a failure status is not evidence* as two separate rules. They are one: **"a terminal status is not evidence, in either direction"**, with on-green and on-failure as its two branches.
  - `planning-and-task-breakdown` had observable-effects criteria, effect-vs-artifact `provides:` identifiers, and prerequisite ordering as three unrelated rules. They are one: **"plans model effects, not artifacts"**, with three numbered corollaries.
- **Counter-example (do not force it)**: Metrics 5 and 6 share a principle and still keep separate numbers, names, and checks, because each catches a defect shape the other's check would miss. A cluster is a distillation candidate when the *checks* collapse, not merely when the prose rhymes.
