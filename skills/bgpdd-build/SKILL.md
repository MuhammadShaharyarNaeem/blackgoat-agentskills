# End-to-End Multi-Agent PDD: Execution Phase (bgPDD-Build)

This Standard Operating Procedure (SOP) coordinates the execution squad (Mason, Nova, Quinn, Luna, Dep, Cipher; Aria as conditional blast-radius advisor; Alex as conditional re-planning agent) to take an existing `plan.md` through building, review, optimization, testing, and deployment prep.

Invoke with `/bgpdd-build` (add the `auto` argument for Autonomous Execution Mode — see §3).

Rationale, observed-failure narratives and examples for every rule below: `references/build-rationale.md`, read on demand. The spine wins on any apparent conflict.

When JSON `null` (a lite-originated epic), there is legitimately no matrix — say so explicitly to the user rather than re-deriving from file absence. When the key is absent entirely (an older state file), fall back to the current file-existence check at step 2.5.

Re-derive at hydration AND after every edit to `plan.md`, including edits you make mid-run.

  - At hydration, establish the working branch: ask the user for the repo's branch-naming convention if unknown; default to `feature/{project-name}`. Create it if it does not exist. NEVER build directly on the default branch (main/master).

Committing is pipeline state management, not application-code writing — it does not violate your no-coding rule.
  - **The commit gate is mechanical — and machine-RUN, not just machine-checkable.** Build the invocation in this order; every step is mandatory unless its condition says otherwise. Rationale: `references/build-rationale.md` § Commit gate.
    1. **Base invocation** (always):
       `python {PLUGIN_ROOT}/pipeline-tools/scripts/check_commit_gate.py --review-report .docs/{project-name}/implementation/review-report.md --state .docs/{project-name}/orchestrator-state.json --milestone "<milestone title>" --changed-files <the milestone's accumulated changed-files union — see Phase 1 step 6> --commit --message "<milestone name + FR/NFR IDs covered>" --verify-tree --ledger .docs/{project-name}/implementation/gates.jsonl`
    2. **`--verify-tree` is always on** — it fails the gate if the working tree holds changes beyond the declared `<changed_files>` plus `.docs/`.
    3. **Add `--require-rendered-evidence`** when the milestone carries `[UI]` tasks, or its surface is `[vs:ui]`/`[vs:web+api]`, AND browser tooling is available on the runtime.
    4. **If the milestone carries `[UI]` tasks and NO browser tooling exists on the runtime, do NOT run this gate for the milestone at all** — **HALT** and surface to the user: the milestone, the fact that the review was necessarily source-only, and the missing-evidence blocker. A `[UI]` milestone is never committed on source-only evidence and never looped against a gate it cannot pass.
    5. **Add the runtime-evidence group** on every milestone whose surface is not `[vs:none]` or `[vs:ui]`: `--require-runtime-evidence --runtime-report .docs/{project-name}/implementation/test-report.md`, **plus every assertion flag you passed at the Phase 2 step 4 gate — `--require-key`, `--expect-status`, `--forbid-host`, `--surface`, `--require-openapi-reachable`, and the `--openapi-doc` trio if you used it. Repeat them all**; the commit gate forwards them to `check_runtime_evidence.py` and folds its verdict into the pass.
    6. **Add `--require-ledger-gates check_runtime_evidence.py`** alongside them — on a `[SEC]` milestone, `--require-ledger-gates check_runtime_evidence.py,check_agent_report.py`. This is what makes a weaker commit-time re-run *detectable* rather than silently the more permissive of the two.
    7. **`[vs:ui]` exemption — the same exemption as Phase 2 step 4 (convention #8)**: a `[vs:ui]` milestone forwards `--require-rendered-evidence` only, never `--require-runtime-evidence`, because the gate the latter feeds cannot accept rendered evidence. `[vs:web+api]` milestones still forward **both** — they carry API captures alongside their UI surface.
    8. **Exit routes.** Exit 0 = gate passed and the commit exists — the script performs the commit, so a skipped gate is loud (no commit) rather than silent. Exit 1 = do not commit; the JSON on stdout names the failing check; route back into the Phase 3 step 4 cycle. Exit 2 = artifact/environment defect — fix the artifact or environment, never hand-wave past it. Full CLI contract (JSON shape, exit codes, parsing rules): `{PLUGIN_ROOT}/pipeline-tools/SKILL.md` — single authority; do not restate parsing rules here.
    - **Blockers precondition — nothing scoped here, and nothing unscoped, may stand.** A milestone commits only when `orchestrator-state.json` holds no blocker scoped to this milestone and no blocker scoped to nothing. An entry scoped to a *different* milestone does not block this one — deliberately looser than this rule's prior "the array must be empty" form (convention #8). `check_commit_gate.py` enforces this split, and `--ignore-unscoped` is its sanctioned override for exceptional cases (contract: `{PLUGIN_ROOT}/pipeline-tools/SKILL.md`).
    - **There is no "commit now, the remaining finding is minor"** — that judgement is exactly what this gate exists to remove.
  - A worker that cannot finish in one run commits its partial work to the same working branch before returning its handoff (this makes the Orchestrator Contract's CONTEXT CHECKPOINTS rule concrete for this pipeline — same branch, commit before returning; see §2).
- **Phase Transitions**: per the Orchestrator Contract §1; Auto Mode (§3) is this pipeline's sanctioned suspension of that confirmation rule.
- **File Artifacts**: All artifacts must use standard GitHub markdown and be saved under `.docs/{project-name}/`.

## 2. Global Safety Mechanisms

Error recovery is the skeleton's section, which points at the Orchestrator Contract §2. This pipeline's refinements, because it is the only pipeline where workers write code:

- **Incremental persistence includes committing.** The instruction you pass every agent must cover code as well as documents: partial work is committed to the working branch (see Git Workflow in §1) before the agent returns, which is what makes the contract's rule enforceable here rather than aspirational.
- **Resumption after interruption** must state exactly what already exists — files *and* commits — so the fresh agent resumes rather than restarting or overwriting finished work.
- **Log discipline.** Every builder/tester delegation is instructed to run builds and test suites through `{PLUGIN_ROOT}/pipeline-tools/scripts/run_quiet.py --log .docs/{project-name}/implementation/logs/<slug>.log -- <command>` when a Python 3 runtime is available. `run_quiet.py` defaults to a 240s timeout; pass `--timeout` explicitly for long suites (e.g. real-DB integration tests). Exit 124 with a `TIMEOUT:` header is a harness result to escalate, never recorded as a test FAIL. Stack skills (e.g. `dotnet-backend-patterns`) carry the no-Python flag fallbacks.
- **Auto Mode raises the stakes on all of the above (§3)**: an unattended run may proceed a long time with nobody watching to restart a lost phase.

## 3. Auto Mode (Optional Argument)

If invoked with the `auto` argument (`/bgpdd-build auto`), operate in **Autonomous Execution Mode**:
- **Macro-Loop Execution**: Seamlessly transition [Phase 1 (Build) → Phase 2 (Test) → Phase 3 (Review) → Phase 4 (Refactor)] in a loop for *each milestone* in `plan.md` without asking for "proceed" confirmation.
- **Phase 5 (Epic Shipping Prep)**: Dep writes the prep `ship-decision.md` (GO/NO-GO) — deploy is deferred to `/bgpdd-shipping`.
- **Phase 6 (Game Tape Checkpoint)**: the Orchestrator appends this run's evidence to `game-tape.md`; Forge runs once at epic end, in `bgpdd-shipping` Step 7.
- **HALT**: Once ALL milestones are complete, drop out of Auto Mode. You MUST ask for explicit human approval before invoking Phase 5 for the entire epic (Phase 6 is a free Orchestrator checkpoint — no approval needed).
- **Circuit Breakers**: If the builder loops 3 times, or Luna flags a blocker the builder cannot fix, immediately drop out of Auto Mode and halt for human intervention.

Non-auto phase-transition reporting: the few-shot example lives in `references/build-rationale.md` § Few-shot handoff example.

## 4. Folder Structure (Semantic Memory)

This is **Tier 2** — the per-enhancement work dir (`.docs/{project-name}/`): this pipeline's read-write workspace, scoped to the current enhancement. **Tier 1** (`.docs/summary/{feature}/`) is the global knowledge base produced by **`/bgpdd-discovery`** — read-only for this pipeline. NEVER write build artifacts to Tier 1.

```text
.docs/{project-name}/
└── implementation/        # Checklists, reviews, and release plans
    ├── plan.md            # Dependency-mapped task list (REQUIRED INPUT)
    ├── environment-manifest.md # Services, repointing map, forbidden hosts, capabilities (Phase 0, user-supplied)
    ├── test-report.md     # Test execution logs and coverage (Quinn)
    ├── review-report.md   # Quality review (Luna)
    ├── acceptance-results.md # Per-step walkthrough results (Quinn, Phase 5 step 2.5)
    ├── ship-decision.md   # Prep GO/NO-GO (Dep, Phase 5); shipping Stage 2 Dep refreshes for final launch
    └── game-tape.md       # Per-phase evidence checkpoints (Orchestrator, Phase 6)
```

The four evidence paths under `implementation/evidence/` — `preflight/`, `build/`, `runtime/`, `review/` — are written and gated by four different parties and **may never be merged**: see `references/build-rationale.md` § Four separate evidence paths.

## 5. Detailed Pipeline Phases

### Phase 0: Verification Readiness (Orchestrator + user, main session)
- **Delegated Agent**: None for authoring — interactive, per the Orchestrator Contract §1 interactive-steps rule. Optionally **Scout** for bounded environment research (step 2).
- **Runs once per session, before the first builder delegation** — not once per milestone (why: `references/build-rationale.md` § Phase 0).
- **Format authority**: the **Environment Manifest** section of `{PLUGIN_ROOT}/runtime-evidence/SKILL.md`. Do not restate or vary its blocks here.
- **Workflow**:
  1. **Resolve the manifest by precedence** (grammar and precedence owned by `runtime-evidence`; do not re-decide them here):
     a. `.docs/summary/{feature}/QA/runtime-environment.md` — the Tier-1 brownfield recipe from `/bgpdd-discovery` Phase 4b. **Authoritative whenever it exists.** Read it and go to step 3.
     b. `artifacts.environment_manifest` in `orchestrator-state.json`, else `.docs/{project-name}/implementation/environment-manifest.md` — written by `/bgpdd-plan` Phase 3.6 or by a prior run of this phase. Read it and go to step 3.
     c. Neither exists (typically a `/bgpdd-lite` epic, which has no Phase 3.6) → author it now, per step 2.
     In every case the facts are durable but the **running processes are not**: step 3's preflight runs even when the manifest was resolved rather than authored.
  2. **If neither exists, author it WITH the user.** Every service's start command, local base URL and readiness check; the repointing map that moves each service and the frontend off shared dev onto the local instances; the forbidden host patterns; the capability inventory the plan's `[vs:]` surfaces require. **This is context the user supplies — do NOT delegate the authoring, and do NOT let any agent infer a value.** You may spawn **Scout** for bounded research into what the repo already declares (compose files, launch profiles, `appsettings.*.json`, CI workflows), writing to `.docs/{project-name}/research/` — research only; the user confirms every value that lands in the manifest.
  3. **Preflight (mechanical) — the minimal subset, not the whole estate.** Select the bring-up steps whose `Needed for` covers the surfaces this plan's milestones actually carry. Then start each selected service, observe its readiness check, and capture the output via `python {PLUGIN_ROOT}/pipeline-tools/scripts/run_quiet.py --capture .docs/{project-name}/implementation/evidence/preflight/<service>-readiness.md -- <the readiness command>`. Then confirm each capability in the inventory is present in **this** runtime: browser automation for any `[vs:ui]`/`[vs:web+api]` milestone, device access for `[vs:rmm]`, a sink client for `[vs:fn]`, an out-of-process HTTP client and a Python 3 interpreter throughout. **A capability is confirmed by exercising it once, not by believing it is configured.** Preflight captures live under `evidence/preflight/`, never `evidence/runtime/`, and must never be reachable by Phase 2's gate.
  4. **A gap is requested now and blocks at the evidence boundary — it does NOT halt Phase 1.** Docker not installed, a service that will not start, an absent browser, an unreachable device, a URL nobody can supply: follow the ladder in `runtime-evidence` (*A missing capability is requested immediately and blocks at the evidence boundary*). Ask the user for it immediately and specifically, and record it in the same action:
     `python {PLUGIN_ROOT}/pipeline-tools/scripts/update_state.py --state .docs/{project-name}/orchestrator-state.json --add-blocker "<the gap>" --blocker-capability <the capability name: browser, docker, device, sink, …> --blocker-source "Phase 0 preflight"`
     Add `--blocker-milestone "<title>"` when the gap only bites one milestone (a browser absent on a plan with a single `[vs:ui]` milestone); **leave the milestone unscoped when the gap blocks every milestone's evidence** — an unscoped entry blocks all of them, which is the correct reading for a missing interpreter or an estate that will not start.
     Then **proceed into Phase 1**. What you must not do is proceed *past* where the gap bites: **Phase 2 does not run against a missing capability**. Nor can the milestone close around it (§1's `[x]`-blocker rule). Clear it with `python {PLUGIN_ROOT}/pipeline-tools/scripts/update_state.py --state .docs/{project-name}/orchestrator-state.json --resolve-blocker "<the blocker's id, e.g. B-2>" --evidence "<the exercise-it-once capture>" --ledger .docs/{project-name}/implementation/gates.jsonl` when the user reports it ready — **resolve by id**, which the add printed, never by a substring of the text, which is exit 2 the moment two gaps share a word.
     - **The one gap that still halts immediately** is one that blocks the *building*, not just the verifying: a schema you cannot inspect, a package feed you cannot reach, a credential the code needs at compile time.
  5. **Inject the resolved manifest path into every builder and Quinn brief** from Phase 1 onward, alongside the milestone text. Take Phase 2's `--forbid-host` arguments straight from the manifest's forbidden-host block — they are declared here precisely so they are not invented there.
  5b. **Persist it as an artifact so `/bgpdd-shipping` inherits it**: `python {PLUGIN_ROOT}/pipeline-tools/scripts/update_state.py --state .docs/{project-name}/orchestrator-state.json --set-artifact environment_manifest=.docs/{project-name}/implementation/environment-manifest.md` (`--set-artifact environment_manifest=null` when step 6 skipped).
  6. **Skip only when every milestone in the plan is `[vs:none]`.** Record the skip and the justification lines it rests on in the game tape, and say so to the user.

### Phase 1: Building
- **Delegated Agent**: **Mason** (Builder, `[API]`/backend milestones) or **Nova** (UI Builder, `[UI]` milestones). Each reads their methodology dependencies (TDD, debugging, SDD) on-demand.
- **Workflow**:
  1. Pick the next milestone — not the stored `milestone_cursor`, and not the one after the milestone you just finished (see the Hydration Phase rule in §1). Do this every time you enter Phase 1, not once per run.
     - **Primary path**: run `python {PLUGIN_ROOT}/pipeline-tools/scripts/next_milestone.py --plan .docs/{project-name}/implementation/plan.md --state .docs/{project-name}/orchestrator-state.json --emit-gate-args --ledger .docs/{project-name}/implementation/gates.jsonl`. Result `NEXT` → proceed with its `milestone_text` and `domain` for the routing step below. Result `MIXED` (exit 1) — including when the script treats `UNTAGGED` as `MIXED` — → the routing rule's planning defect (step 2): **halt** and surface it, do not improvise a split. Result `DONE` → skip ahead to Phase 5's completion gate.
       - `--emit-gate-args` returns a `gate_args` object (`surface`, `expect_status`, `require_keys`, `forbid_hosts`) parsed from the milestone's `RUNTIME PROBE:` line. **Carry it forward to Phase 2 step 4 — convention #9 in force** (why: `references/build-rationale.md` § `--emit-gate-args`). If `gate_args` is null for a field, read that field off the `RUNTIME PROBE:` line yourself.
       - `--ledger` surfaces an advisory `unbacked_complete` list — milestones marked `[x]` with no PASS commit-gate entry behind them. Treat any entry as a state defect and surface it before building further.
  2. **Route by domain.** Read the domain off the milestone's tasks' domain tags (`[API]` or `[UI]`, assigned at planning). Route the whole milestone to the matching builder: `[API]` tasks go to Mason, `[UI]` tasks go to Nova. A milestone mixing `[UI]` and `[API]` tasks is a PLANNING DEFECT: **halt** and surface it to the user for re-planning (route back through Alex) — do NOT improvise a split yourself. An `UNTAGGED` milestone (no `[UI]`/`[API]` on heading or tasks) is the same class of planning defect as `MIXED` — halt and surface it; do not invent a route.
  3. Delegate the milestone to a **single builder agent (Mason or Nova per the routing rule)**, who builds its tasks in plan order. **The milestone is the unit of delegation — do NOT fan the milestone's tasks out to parallel builder agents**, even when their `Dependencies:` fields show no ordering constraint between them (why: `references/build-rationale.md` § Why one builder per milestone). **CRITICAL CONTEXT HANDOFF**: copy the exact text of the active milestone from `plan.md` into the delegation prompt so it knows exactly what to build.
     - **Point the builder at the probe it is already holding.** The pasted milestone text already carries the `[vs:<surface>]` tag and the `RUNTIME PROBE:` line inside its `### Checkpoint:` block. Quote both into the brief explicitly, exactly as Phase 2 step 1b does for Quinn, and instruct the builder to run the declared probe as a **self-check** written to `.docs/{project-name}/implementation/evidence/build/` — never `evidence/runtime/`, which is the verifier's gating path. This adds no gate: Phase 2's Runtime Evidence Gate still runs solely against Quinn's independent capture.
  4. **STRICT BLAST RADIUS RULE**: Instruct the builder that *before* modifying any shared DTO or library, it MUST trace dependencies by searching the codebase for all consumers of the DTO/library. If the radius extends beyond its active microservice, it must document it in its handoff and return for architectural review.
  5. If the blast radius exceeds the active microservice:
     a. Notify the User: "Blast radius exceeds the current microservice boundary. Architectural review required."
     b. Delegate to the **Aria** agent as a temporary advisor (**Mode 2 — Scoped Advisory** in her `blackgoat-research` methodology — she must NOT write or modify `detailed-design.md` in this mode), passing her the builder's blast-radius report; ask for a scoped architectural recommendation returned in her `<handoff>`.
     c. Present Aria's recommendation to the User for approval.
     d. After approval, delegate a **fresh builder** agent (same builder as this milestone's routing), passing it the prior handoff state and Aria's ruling.
  6. Read the builder's returned handoff and extract the strict `<changed_files>` XML list from it. **Accumulate, do not replace**: the milestone's changed-files set is the union of the builder's `<changed_files>` here, Quinn's `<changed_files>` from Phase 2 and every retest round, and any Phase 3/4 remediation `<changed_files>` — accumulated across the whole milestone, never replaced by the last handoff. This accumulated union is what feeds `--changed-files` at the commit gate (§1).
  7. **Record the delegation** (Orchestrator Contract §4 owns the rule; `{PLUGIN_ROOT}/pipeline-tools/SKILL.md` owns the CLI):
     `python {PLUGIN_ROOT}/pipeline-tools/scripts/record_run.py --log .docs/{project-name}/implementation/run-log.jsonl --pipeline bgpdd-build --phase "Phase 1" --event delegation --agent <mason|nova> --model <tier> --unit "<milestone title>"`
     plus `--duration-s`/`--tokens-in`/`--tokens-out` (or `--from-json <the completion payload>`) from the runtime's completion notification, and `--status` from the handoff. Phases 2, 3 and 5 repeat this on their own returns with their own `--phase`/`--agent`; only the first occurrence spells the invocation out.

### Phase 2: Testing
- **Delegated Agent**: **Quinn** (QA Tester). She reads her methodology dependencies (runtime-evidence always; TDD when authoring new test code; debugging and playwright as scoped) per her dependency table.
- **Workflow**:
  1. Delegate to the **Quinn** agent. **CRITICAL CONTEXT HANDOFF**: pass her the exact text of the active milestone and the `<changed_files>` list from the builder. **CRITICAL PATHING**: instruct her to append results to `.docs/{project-name}/implementation/test-report.md`. If the milestone contains `[UI]`-tagged tasks, inject the resolved path of `{PLUGIN_ROOT}/ui-design-patterns/references/component-mechanics.md` — Quinn derives her [UI] assertions from it (each citing the item's CM-id).
  1b. **Route the runtime probe into her brief.** The milestone's `### Checkpoint:` block is already inside the verbatim `milestone_text` you pasted in step 1 (level-3 headings never terminate a milestone block — why `planning-and-task-breakdown` forbids `## Checkpoint:`). ### Phase 6: Game Tape Checkpoint (Orchestrator)
- **Delegated Agent**: None — the Orchestrator performs this phase directly. No delegation, no halt.
- **Cadence — this is NOT an end-of-run phase.** It is numbered 6 only because it is described last. Per the Orchestrator Contract §4, evidence checkpoints fire **at every state persistence**: you run step 1 below **each time a milestone closes and you update `orchestrator-state.json`**, in the same step, and again at epic end as a roll-up (step 2). A checkpoint deferred to the end of the pipeline records nothing (why: `references/build-rationale.md` § Phase 6).
- **Workflow**:
  1. **Per milestone (mandatory, at the cursor update).** Append to `.docs/{project-name}/implementation/game-tape.md` under a `## bgpdd-build — [milestone] — [date]` heading (create the file if it does not exist). 3–6 bullets **per milestone** — a deliberate refinement of the skeleton's default once-per-run, at-most-10 cap (convention #8). Written while the milestone is still in your context: user corrections made, agent failures/retries, re-delegation rounds and why, circuit-breaker trips, which gates were genuinely exercised versus rubber-stamped (read off step 1b's pasted table, not off memory), every BLOCKED or proxy-substituted verification an agent reported, and the runtime exit criterion you personally observed — recorded as the **verbatim command plus its captured output block**, never a summary of it (or, if you could not observe it, exactly what blocked you). **No pasted output, no claim**: an exit criterion logged as "observed" or "passed" with nothing showing it is worth less than an empty entry, because it looks like evidence and will be read as evidence by the improvement run months later. Record what actually happened, including your own mistakes — a checkpoint that only logs successes is a checkpoint that has learned to lie.
  1b. **Paste the milestone's telemetry block; do not write prose about what it cost.** Under those bullets, paste the verbatim output of
     `python {PLUGIN_ROOT}/pipeline-tools/scripts/summarize_run.py --run-log .docs/{project-name}/implementation/run-log.jsonl --ledger .docs/{project-name}/implementation/gates.jsonl --unit "<milestone title>" --markdown`
