# Agent Audit Skill

## Purpose
To ensure that autonomous agents operating in a squad or pipeline do not suffer from conflicting constraints, broken escalation paths, or output format collisions that would cause them to hallucinate, crash, or disobey instructions.

## When to Use This Skill
- When a subagent fails to complete a task or outputs the wrong format.
- When expanding a squad with a new agent and you need to ensure they align with the base persona.
- When refactoring a project's methodologies.
- Trigger phrases: "audit this agent", "check the squad for conflicts", "validate [agent] persona"

## Execution Checklist

Before beginning the audit, you MUST read the deep-dive explanations of the heuristics located at:
`{PLUGIN_ROOT}/agent-audit/references/heuristics.md`

Three facts from that file govern the whole checklist, so they are not repeated per step: the metrics fall into **families** that share one principle (context economy 3/8/10; one-rule-one-home 5/6/18; existence-vs-agreement 15(c)/16/17; existence-vs-bite 19/20/21), **Metrics 16, 17 and 18 are existence checks on mechanisms and prose — they never score a pipeline's output documents**, and **Metrics 19–21 are the only metrics that execute something: they run the gates, the lints and the eval records, and a metric that could have been run but was eyeballed is recorded as NOT RUN, never PASS.** Metric numbers are cited across the plugin; never renumber, only append.

Once you understand the audit metrics, execute the audit following these steps:

0. **Discovery (locate the files before reading)**: You cannot audit what you cannot find. First:
   - **Resolve `{PLUGIN_ROOT}`** to the actual directory this skill was loaded from (it varies by install location — do not assume an absolute path). Typically the `skills/` directory, two levels up from a skill's `SKILL.md`.
   - **Locate the target persona** (the agent's `SKILL.md`, or an `agents/<name>.md` file) and read its **"Methodology Dependencies" table** — this table names every inherited file (`base-persona.md`, methodology `SKILL.md` files) and when each is loaded.
   - **Glob/grep for every referenced dependency** and confirm each path resolves to a file that exists on disk. Flag any dangling reference immediately (a dependency pointing at a file that does not exist is an automatic Blocker).
   - **Locate any project overrides**: `.agents/AGENTS.md` in the target project.
   - **List everything you found** (and any missing files) before proceeding to the metrics.

0.5. **Mechanical preflight (run before reading any prose)**: The 2026-08-30 audit passed all 18 metrics while three frontmatter blocks on disk failed to parse and two shipped skills had never registered in any runtime — because every metric was applied by reading. Run these, record each command and its exit code in the report, and only then start reading:
   - `python {PLUGIN_ROOT}/pipeline-tools/scripts/check_frontmatter.py <plugin root>` — any error is a Blocker before Metric 11 is even opened.
   - `python {PLUGIN_ROOT}/pipeline-tools/scripts/check_dependency_tables.py {PLUGIN_ROOT}`.
   - **Registration diff**: compare the set of `skills/*/SKILL.md` and `agents/*.md` on disk against the set the runtime reports as loaded (in a runtime that lists loaded skills and spawnable agent types at session start, that listing; otherwise the runtime's equivalent registry). A file on disk that the runtime does not list — or lists with an empty description — is a Blocker: the plugin believes it shipped something the user cannot invoke.
   - Every `pipeline-tools` script's `--self-test`, plus `test_check_coverage.py`. A failing self-test is a Blocker; a script with no self-test is a Warning under Metric 19.
   - `grep -rn "check_[a-z_]*\.py\|next_milestone\.py\|update_state\.py --resolve-blocker" skills/bgpdd-*/SKILL.md | grep -v -- --ledger` — feeds Metric 20; any hit is a FAIL there.
   - The eval record summary for Metric 21: per case, latest-window pass rate, run count, and the harness version/provenance fields present.
   A preflight command that cannot be run (no interpreter, no runtime listing) is reported as BLOCKED with the reason — never skipped silently, and never replaced by a read.

1. **Read Target Files**: Read the target agent's `SKILL.md` file AND all underlying methodology skills (the `SKILL.md` of each skill) they inherit.
2. **Apply The Golden Rule (Who vs. How)**: The Persona (the agent's `SKILL.md` / `agents/<name>.md`) defines WHO the agent is. The methodology skills (each skill's `SKILL.md`) define HOW they work. This is a critical distinction—never let procedural 'How' instructions pollute the identity 'Who' file.
3. **Apply Metric 1 (Interface Alignment)**: Ensure upstream outputs match downstream inputs. Also verify **writer ownership**: every pipeline artifact has exactly ONE declared writer. Two skills instructing two different actors to write the same path is an output collision and an automatic **Blocker** — regardless of whether either side says "append". Check write-order against phase-order too: an artifact written in an earlier phase than the phase whose owner creates it is a collision even when only one owner is named.
4. **Apply Metric 2 (Dependency Conflict)**: Ensure inherited methodology skills don't contradict the agent's core function. Also flag any **unfollowable MANDATORY**: a rule marked mandatory that presumes a runtime capability this plugin does not guarantee (background delegation with completion notifications, a specific tool surface, a persisted transcript). In a runtime-neutral plugin such a rule must state the capability as a precondition AND sanction an explicit fallback for runtimes lacking it. An unfollowable MANDATORY is worse than a strong SHOULD — the agent must either violate a hard rule or invent its own fallback silently, and you will never see which it chose.
5. **Apply Metric 3 (Role Cohesion)**: Identify specific API or framework rules bloating the persona. Do not blindly delete all Procedural Memories; use the **Abstraction Rule**:
   - Universal Engineering Principles (e.g. Data Safety) must be KEPT and elevated.
   - Specific project bloat should be generalized into language-agnostic principles if possible.
   - Irreducible project bloat must be moved to the project's `.agents/AGENTS.md`.
6. **Apply Metric 4 (Escalation Hallucination & Path Validity)**: Validate the chain of command for blockers. Ensure isolated subagents are not instructed to manage pipeline state transitions.
7. **Apply Metric 5 (Token Efficiency)**: Look for redundant or conflicting formatting instructions. Ensure generic methodologies do not overwrite persona-specific output formats.
8. **Apply Metric 6 (DRY & Contract Reuse)**: Ensure methodologies are shared rather than duplicated.
9. **Apply Metric 7 (Orchestrator vs Methodology Collision)**: Ensure the methodology does not attempt to orchestrate a swarm or manage state transitions that belong to the Orchestrator. If necessary, split the methodology into explicit "Modes".
10. **Apply Metric 8 (Context & File Bloat)**: Check the persona's "Methodology Dependencies" table. Ensure only the absolute bare minimum files are loaded "Always", and that heavy methodology files are strictly loaded on-demand.
11. **Apply Metric 9 (ID Traceability)**: Ensure requirements generate stable IDs (`FR`/`NFR`) and that every downstream stage threads them through — planning tasks cite the IDs, tests exercise them, and coverage gates check them. Flag any link that drops the ID or falls back to unverifiable prose-matching.
12. **Apply Metric 10 (Wake-Up Context Weight)**: Measure, don't guess. Count the words of the persona file PLUS every "Always"-loaded Methodology Dependency (e.g. `wc -w`). Flag any agent whose unconditional wake-up load exceeds ~2,500 words, and any methodology `SKILL.md` that is not a lean spine (`## Worker Execution Contract` + `references/` deep-dive).
13. **Apply Metric 11 (Frontmatter & Metadata Hygiene)**: **Parseability first, consistency second.** The preflight's `check_frontmatter.py` result is this metric's first line: a block that fails to parse fails everything downstream of it silently (the skill or agent is simply not registered), so a parse error is a Blocker regardless of how consistent the rest looks. Then check consistency across the squad — `phase:` labels form one coherent, collision-free sequence, `model:` tiers exist and fit, `description:` matches what the file actually does and stays under the runtime's truncation length, every `bgpdd-*` pipeline carries its `trigger:`, and `depends-on` names real agents **and is complete**: every agent whose output a pipeline routes into this one must appear (a builder split into two personas must appear in every downstream agent's list, not just the original). Finally, **docs mirror the tree**: user-facing docs (README, runtime setup docs) enumerate every pipeline and skill on disk, and every count they cite (metrics, agents, pipelines) matches what is there; an undocumented shipped pipeline or a stale count is a Warning.
14. **Apply Metric 12 (Trigger Collision)**: Ensure worker methodologies do not carry end-user trigger language in their `description:` that competes with the orchestrator pipelines. Worker methodologies must self-identify as squad-internal execution contracts; user-facing triggers belong to the pipeline skills.
15. **Apply Metric 13 (Cross-Pipeline Consistency)**: **First, verify every `bgpdd-*` pipeline actually loads `agent-squad/orchestrator-contract.md`** — grep each pipeline for the mandatory-read reference and confirm the path resolves. The shared Orchestrator rules (background execution, circuit breaker, incremental persistence, role boundaries) were deliberately de-duplicated OUT of the pipelines into that one file, which trades a visible duplication defect for an invisible omission defect: a pipeline that silently fails to reference the contract loses those rules entirely, with **no symptom at all** until an unbounded or work-losing run happens. A missing or unresolvable reference is an automatic **Blocker**, as is any pipeline that re-inlines a contract rule instead of referencing it (re-inlining restarts the drift this consolidation removed). Then ensure sibling orchestrator SOPs share the same hardening skeleton — Path Resolution, Global System Constraints, Global Error Recovery + circuit breaker, state hydration/persistence (`orchestrator-state.json`), and a Game Tape evidence checkpoint (per-phase pipelines) feeding the single end-of-epic agent-improvement run (bgpdd-shipping). Flag any pipeline missing pieces its siblings have. Treat `orchestrator-state.json` as an inter-pipeline interface, not per-pipeline scratch: verify producer/consumer field-level completeness across sibling pipelines — every field a downstream step reads must exist in the schema the upstream pipeline writes (a field written by one pipeline and silently absent when a sibling reads it is a Blocker). One deliberate asymmetry: the Phase 2.5 Adversarial Design Gate is bgpdd-plan-specific by design (design documents only exist in that pipeline), so its absence from sibling pipelines is NOT a symmetry defect. Two further checks belong here. **Re-entry closure**: every route one pipeline names into another ("route back to `/bgpdd-build`", "defects go to `/bgpdd-bugfix`") must be accepted by the target pipeline's hydration or entry check for the state the source pipeline leaves behind — a documented fix route that the target's whitelist rejects is a Blocker (shipping's exit-2 route into build was one). **Bound labeling**: extract every numeric bound (rounds, follow-ups, bullets, minutes, axes) across the pipelines and their methodologies; two bounds on the same concept that differ without a convention-#8 label naming the rule refined is a FAIL, the same unit-mismatch class as "2 per artifact" vs "2 per checklist area".
16. **Apply Metric 14 (Model Assignment Fit)**: Ensure each agent's `model:` tier matches its task complexity — lightweight scanners on small/fast tiers, architecture/planning/code-writing/meta-editing agents on top tiers, everything else mid-tier — **with one ordering rule that overrides the tier list: an agent whose verdict gates another agent's output must run at a tier at least equal to the producer it judges.** A sonnet reviewer over opus builders is an inversion, not "everything else mid-tier", because the whole point of the gate is to catch what the stronger model missed. Producers that a script fully verifies (a refactorer whose tests are the judge) may run lower.
17. **Apply Metric 15 (Skill Content Validity & Cross-Skill Contract Coherence)**: Verify the skill's documented content is correct, not just well-structured — (a) every code sample compiles/runs against the real implementation (no undeclared dependencies or missing wiring/registration); (b) the skill is internally non-contradictory and no sample violates its own doctrine; (c) for any producer/consumer contract between two skills — a runtime wire shape (a backend response envelope and its frontend consumer) **or** a document convention a tool parses (field grammars, ID formats, heading shapes) — **first verify the contract is documented at BOTH ends, then verify the two ends agree.** A one-ended machine contract is a **Blocker**: a grammar documented only on the consuming/validator side is unreachable, so the check never fires and a check that never fires is indistinguishable from a passing one. Where both ends exist, both must describe the SAME serialized wire shape and name the serialization policy (field names, casing, scalar-vs-object), not each side's source-language declaration shape; (d) **trigger phrasing matches intended cadence** — flag any rule whose trigger clause ("when finished", "at the end", "once complete") gates an action that should be happening throughout, which teaches deferral.
18. **Apply Metric 16 (Defect-Class Enforcement)**: Verify the pipeline's methodology skills *contain* the defect-class enforcement rules. **Grep the live files — distillation passes relocate these rules without deleting them, so a rule found under a new heading still passes.** The inventory: `blackgoat-research` — the `## Divergence & Supersession Register` heading, the requirements write-back (carrying **NOT complete until**: a supersession needs BOTH a register row AND an in-place `requirements.md` annotation), and the closing **Brief-Conformance Diff** step; `bgpdd-plan` — the Phase 2.5 Adversarial Design Gate with its 6-item attack list (crash windows, reversals, races, trust-boundary amounts, state-machine self-consistency, config knobs); `planning-and-task-breakdown` — **observable effects** criteria and external-prerequisite ownership (corollaries 1 and 3 of *Plans model effects, not artifacts*), the `provides:`/`consumes:` grammar the lint parses, the **negative-half proof** on every gate-authoring task, the **declared-gate-needs-executor-wiring** rule (manifest script name AND CI job as task steps), and *sequentially with a single builder*; `pipeline-tools` — **four** lints with tests: `literal-count`, `consumes-provides`, `path-hygiene` (plan mode) and `supersession-annotation` (design mode). A missing or weakened rule = FAIL naming the skill and the rule. **Do not over-credit the fourth lint**: `supersession-annotation` catches register-rows-without-annotation only; a divergence never filed, or filed outside the register section, remains the Phase 2.5 gate's job.
19. **Apply Metric 17 (Output-Rubric Gate Coverage)**: Verify each of the 8 output-quality dimensions — brief coverage; structure & testability; honing quality; domain/financial correctness; completeness & reachability; infra answer quality; internal consistency & traceability; signal-to-noise — maps to at least one *enforcing mechanism* (a phase gate, a checklist item, or a lint) somewhere in the pipeline's methodologies. An uncovered dimension = Warning (not Blocker), naming the dimension.
20. **Apply Metric 18 (Convergent Redundancy / Distillation)**: Find clusters where multiple rules, bullets, or lines encode the same underlying thinking, and flag each cluster as a distillation candidate — merge the prose upward into one stated principle with corollaries, push the enforcement downward into a mechanism (a lint, a gate attack item, a schema or template constraint), and move rationale to `references/`. Cite the cluster's lines and name the shared principle. Severity: **Warning**. Two constraints on the fix: a merge that lands no mechanism has traded enforcement for brevity, and **numbered identities are never renumbered** — merge the text, keep every number, name, and distinct check.
21. **Apply Metric 19 (Gate Adversarial Proof)**: Metrics 15–17 ask whether a gate *exists*; this one asks whether it *bites*. For every gate script and every mechanical lint the pipelines invoke, **author the minimal fabricated input that claims the work was done without doing it** — a `PASS` line with no evidence, an `Approve` with no findings, a hand-typed capture, a zero-byte image, a `GO` inside a fenced template, a hand-appended `[x]`, a `touch`ed report — and **run the gate against it in a scratch directory.** A gate that exits 0 on fabricated input is a Blocker naming the fabrication. Then check the three provenance properties every load-bearing gate needs: (a) it reads at least one thing the author cannot type (a hash, a tool-written sidecar, a ledger record, a filesystem or git fact); (b) freshness is not a caller-supplied or `touch`-able proxy alone, and a gate that re-reads an artifact produced several phases earlier without re-execution is stale by construction; (c) every hardening flag defaults closed or is forced by the pipeline text — a flag that is opt-in and chosen by the party being gated is a Warning. A script with no `--self-test` is a Warning here as well.
22. **Apply Metric 20 (Gate Invocation Coverage & Lane Parity)**: Existence of a gate is worthless if a pipeline step can skip it silently. **First, the ledger grep from the preflight must be empty**: every gate, `next_milestone.py`, and `update_state.py --resolve-blocker` invocation in every pipeline carries `--ledger`, and the commit gate carries `--require-ledger-gates` for the gates its milestone type depends on. **Second, lane parity**: every lane that ends in a commit or a ship decision — including the light ones (bugfix, lite, verify) — must have a named state file, a game-tape write at each state persistence, at least one mechanical gate between the last agent verdict and the commit, and a closure path that only a script can perform (`mark_milestone.py` or the commit gate itself). A lane with a prose-only close is a Blocker; the most-used lane is the one most likely to be ungated, so check the light lanes first. **Third, no hand transcription**: any gate argument the pipeline tells the Orchestrator to copy from an artifact by eye (assertion keys, expected statuses, changed-file unions) when a script could emit it is a Warning naming the script that should.
23. **Apply Metric 21 (Eval-Suite Health)**: The eval suite is the only instrument that measures the plugin itself, so audit it as an instrument. Using the preflight summary: (a) **every suite has actually run** — a suite with zero records is a Blocker regardless of how good its cases look (the trigger suite sat unrun for weeks); (b) **records carry provenance** — plugin commit, model/CLI version, case hash — or cross-time comparisons are fiction (Warning); (c) **red cases are triaged, not reported** — for each case below threshold, classify the latest failures as GRADER, FIXTURE, CONTRACT, AGENT, or INFRA before it enters the findings; a grader fixed after the last run leaves a stale red that must be re-run, and **a run that finished in seconds, produced no artifact, or hit a CLI/quota error is INFRA and is excluded from the pass rate, never counted as an agent failure**; (d) **the judge cannot be fooled by the answer's wording** — a routing or verdict judge that string-matches a name passes a response that rejects it, so prefer a tool-use or artifact-shape signal; (e) **the Orchestrator has at least one eval** — an isolated persona suite says nothing about routing, phase gating, or hand-offs; (f) graders read artifacts with an explicit encoding and tolerate the platform's line endings. Severity: (a) and INFRA-counted-as-FAIL are Blockers; the rest Warnings.

## Verify (close the loop)

After the surgery plan is applied, **re-run the preflight and all 21 metrics against the patched files** and confirm every `FAIL` flips to `PASS`. Report any residual `FAIL`s explicitly — do not declare the audit complete while a Blocker remains. **Surgery that changes a gate's contract (a new required artifact, a stricter parser, a moved template line) has a migration cost for in-flight projects**: name it in the surgery plan, state what an artifact authored under the old contract now does (fails closed, warns, is waived by which flag), and re-run the eval cases that exercise the changed gate before calling the surgery verified — a surgery verified only by self-tests has been verified against fixtures the surgeon wrote.

- **Grep for stale references after any rename, reorder, terminology change, or policy flip.** After applying any rename, reorder, or terminology change, grep the ENTIRE plugin tree for every occurrence of the old value (old name, ordering token, renamed term) before declaring surgery complete. A fact mirrored across persona prose, trigger anchors, coverage tables, and pipeline steps is only fixed when zero stale references remain — patching the canonical definition alone is not sufficient. Renames/reorders are the top source of residual FAILs that survive a first pass.

  **Policy reversals get the same sweep, and are easier to miss because nothing textual changed.** After changing a policy — enabling or forbidding a practice — grep the tree for prose that still assumes the retired behavior: rationale paragraphs, "Opportunities" sections, worked examples, and deep-dive narratives. A policy is only flipped when zero prose still advertises the old one. A skill that forbids a practice in its rules while its narrative still recommends it will be followed as the narrative, because the narrative is where the reasoning lives.
